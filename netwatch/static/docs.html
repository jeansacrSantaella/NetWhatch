Resumen

Monitoriza tu red local con netwatch. Encuentra el backend en netwatch/; ejecuta estas tareas en paralelo:

  1. Inventario: encuentra equipos con un barrido de ping y la tabla ARP.
  2. Caídas: comprueba cada 5 segundos la red local, internet y DNS; registra cada caída y recuperación.
  3. Calidad: mide latencia, jitter y pérdida por destino y equipo; prueba la velocidad cada hora.
  4. Alertas: configura Telegram para recibir avisos de caídas, equipos nuevos y cambios de IP pública.

Consulta los datos en SQLite (netwatch.db) y en el dashboard, servido desde el servidor web local.

Librerías

No instales dependencias: usa la librería estándar de Python 3 y comandos del sistema operativo. Construye el dashboard con HTML, CSS y JavaScript sin frameworks; dibuja las gráficas en SVG.

Comandos del sistema y servicios externos

  • ping: usa -W en milisegundos en macOS y en segundos en Linux. ping() ajusta el valor según el sistema.
  • arp -an e ip neigh: lee ambas tablas de vecinos (IP a MAC) y combina sus resultados.
  • route -n get default (macOS) o ip route show default (Linux): dirección del router.
  • Consulta api.ipify.org para la IP pública, speed.cloudflare.com para la velocidad y api.telegram.org para las alertas. Descarga una vez la lista de fabricantes desde standards-oui.ieee.org a oui.txt.

Principios SOLID aplicados

  • Responsabilidad única: asigna una función a cada monitor, repositorio y widget.
  • Abierto/cerrado: añade mediciones con PeriodicTask, registra alertas en EventBus, endpoints en Router y tarjetas en main.js, sin modificar componentes existentes.
  • Sustitución de Liskov: implementa el contrato run_once()/interval en cada tarea y update(summary) en cada widget.
  • Segregación de interfaces: inyecta en cada clase solo las dependencias que necesita. Por ejemplo, pasa internet_up() a SpeedMonitor en vez del monitor de conectividad completo.
  • Inversión de dependencias: inyecta repositorios y funciones de red (pinger, read_arp…) en monitores y servicios. Así puedes probarlos con SQLite en memoria y redes simuladas.

Lógica de detección

Caídas de red local, internet y DNS

En cada ciclo, ConnectivityMonitor consulta por ping y DNS el router y los destinos externos. Evalúa estos tres estados:

  • Red local: marca la conexión como correcta si responde el router; si no detectas el router, asume que la red local funciona.
  • Internet: marca la conexión como correcta si responde 1.1.1.1 o 8.8.8.8.
  • DNS: marca el servicio como correcto si responde al menos un servidor DNS.

Atribuye los fallos en cascada: si cae la red local, no marques internet como caído; si cae internet, no marques DNS como caído.

ServiceState.update() evita falsas alarmas. Exige 3 fallos seguidos (fails_to_alert) para registrar *_down y fecha la caída en el primer fallo. Registra *_up con la duración total cuando vuelve la conexión.

Registra monitor_gap si pasan más de 20 s (4 × probe_every) entre ciclos; normalmente indica que suspendiste el equipo.

Consulta DNS hecha a mano

dns_query() arma un paquete DNS (cabecera con id aleatorio, recursión activada y pregunta tipo A para example.com), lo envía por UDP al puerto 53 y da la respuesta por buena si coincide el id, el código de respuesta es 0 y hay al menos una respuesta.

Inventario de equipos

  1. Obtén la IP local con local_ip() y calcula la subred x.y.z.0/24.
  2. Haz ping a las 254 direcciones con 64 hilos para llenar la tabla ARP; no necesitas las respuestas.
  3. Lee la tabla con read_arp() y descarta entradas incompletas, broadcast y multicast.
  4. Guarda cada equipo nuevo con su nombre DNS inverso y publica new_device. Incluye el fabricante y marca si la MAC es privada (bit 0x02 del primer byte, común en teléfonos).
  5. Marca un equipo como desconectado tras 3 escaneos seguidos sin detectarlo (misses_to_offline) y publica device_offline. Si vuelve, publica device_online.

Omite las alertas de equipos nuevos durante el primer escaneo con la base vacía (notify=False) para no recibir un aviso por cada equipo de casa.

Calidad: latencia, jitter y pérdida

Pasa a quality() las mediciones ordenadas de la última hora:

  • Latencia: media de los tiempos de las respuestas correctas.
  • Jitter: media de la diferencia absoluta entre cada respuesta y la siguiente.
  • Pérdida: porcentaje de mediciones sin respuesta.

Disponibilidad de 24 horas

Divide el día en 144 tramos de 10 minutos y calcula los aciertos por servicio en cada uno. Si pruebas varios destinos (por ejemplo, los dos de internet), cuenta el mejor. La cinta marca en verde ≥ 99 %, en ámbar ≥ 90 % y en rojo los valores inferiores. Calcula la disponibilidad como la media de los tramos con datos.

Prueba de velocidad

SpeedTester.measure() descarga 10 MB y sube 3 MB de datos aleatorios a Cloudflare. Calcula los Mbps con bytes × 8 / segundos y omite la prueba si falla internet.

Escáner de host

HostScanner.scan() resuelve el nombre, consulta DNS inverso, envía 4 pings para medir latencia, jitter, pérdida y TTL, busca la MAC en ARP y el inventario, prueba DNS y conecta por TCP a cada puerto (256 hilos, 0,5 s por puerto). En cada puerto abierto, lee el banner; si usa HTTP, envía HEAD y muestra la cabecera Server.

Alertas por Telegram

Suscribe TelegramNotifier al EventBus para encolar hasta 100 eventos de alert_kinds con notify activo. Un hilo los envía en orden y reintenta cada 30 s si falla la conexión. Marca los reintentos como "enviado con retraso" y descarta respuestas 400/401/403/404 (token o chat incorrectos).
